设备手册检索问答系统
先把「是哪台设备」问清楚

运维问「万用表怎么测电流」时不会报型号。这个系统的核心不是把大模型接到手册上，而是把「确认型号」做成一门不可跳过的产品环节—— 型号确认了才进召回，召回够了才允许开口，开口就必须能指回原文哪一段。

01背景与问题

设备运维和售后客服每天要查三十次以上手册。他们的提问方式和手册的写法之间有一道天然的沟：手册按型号分册、按章节组织， 而人只会说症状。系统擅自替用户在几个型号里选一个来答，等于给了一个错答案，而运维会照着这个答案去接线。

三条来自现场的硬约束

约束现场表现对产品的含义
只说症状「万用表怎么测电流」「网关一直闪红灯」，型号缺省或说错入口必须做实体对齐与消歧，且不能静默替用户选
图文混排接线图、规格表被当纯文本切碎后读不懂切片要以标题层级为结构主键，图片另走摘要与原文回链
要能照着做答案不能指回原文那一段，运维不敢执行引用不是加分项，是能否交付的前置条件

现状诊断：检索栈够了，产品没闭环

链路上已经搭好稠密 + 稀疏的混合检索、HyDE 与联网并行、RRF 融合、断崖式精排截断这一套。真正拖住使用意愿的不是算法， 而是四件事：文档管不了、答案验不了、会话撑不住、挂了说不清。手册改版只能再传一份、库里旧参数还在被召回； 答案拼了片段 ID 却不回传给前端，客服没法证明这句话出自第 3 章；会话状态存在浏览器的一个字段里，换个窗口就断； 任务和流式队列全在进程内存，重启就丢。

这份 PRD 的排序依据不是「技术上难不难」，而是「不修会不会被现场同事骂」。按这个尺子量， P0 全是日常闭环缺口，不是算法问题。

02目标与非目标

北极星指标：一次问对率。定义为首次回答即可照着操作、不需要人工兜底的比例。 之所以不用「答案准确率」，是因为在运维场景里，一个无法执行的正确答案等于错答案；而一个「我不知道，转人工」的诚实回答，损失远小于一次错误接线。

目标拆成三层，各自定指标

层要解决什么主指标门槛
消歧层问句里的设备是哪个型号型号确认准确率≥ 80%
检索层正确片段有没有被召回并排进前列Recall@5 / Hit@5≥ 0.95
生成层答案有没有依据、能不能点开引用可点率 / 无依据作答率100% / ≤ 1%

三层分开定指标，是因为合成一个总分会让短板互相掩盖：检索退化和拒答退化在总分里看起来一模一样。

明确不做（本期）

  • 不做通用文档助手。多品类混库后，断崖截断的阈值和型号命名的规则都要重标，收益不成立。
  • 不做多租户 SaaS。鉴权与租户隔离排进 P2，先把单班组用顺。
  • 不调模型权重。先修索引和交互——切片重复率这类问题微调救不回来。
  • 不做写操作自动化。下单、改配置这类动作只生成「待确认操作」，由人执行。

03用户与场景

同一个系统要服务三种完全不同的问法，它们的失败模式不一样，验收口径也不能共用一套。

场景典型问句期望行为当前失败模式
型号明确型 「H3C LA2608 的默认网关是多少」 直接检索并给出带引用的答案 基本可用，偶发被无关片段挤占
型号模糊型 「万用表怎么测电流」 抽出品类 → 与库内真实型号做向量对齐 → 歧义时给候选让人点 只返回文本候选，手机上手输完整型号；下一轮又要重新识别
多跳步骤型 「换了电池还是要重新校准吗」 承接上文已确认型号，跨小节拼步骤 会话状态靠单字段维持，指代容易飘到错的轮次

优先级判断：先做型号模糊型。它同时决定准确率和信任——这类问法答错，用户不会认为是「检索没做好」， 而会认为「这系统不懂我在说什么」，之后就不再用了。

04需求池与优先级

每条需求都标了判断依据（对应到具体实现位置）与验收标准。这样争议不落在「我觉得重要」，而落在「这条验收过不过」。

P0 · 不修就没法日常用

ID需求依据验收标准状态
R-01 型号确认做成可点选的三态交互，并在会话内锁定 已有高/中置信度阈值与同类候选，但只回文本，也没有锁定状态 候选可一键点选；锁定后同会话不再重识别；手机端不用手输型号 部分
R-02 答案结构化引用：正文角标 + 侧栏片段卡片 + 历史回放可点 上下文里已带片段 ID、标题、分数，但答案与历史都不落引用 角标点开可见文件名 / 章节 / 页码 / 原文图；刷新与回放后仍可点 待做
R-03 文档生命周期：列表、按文档删除、重传覆盖 入库只有插入，没有按文档维度的更新与删除 手册改版后旧版不再被召回；删除后检索零命中；列表能看出谁覆盖了谁 待做
R-04 多会话、会话重命名、历史正序拼装 前端只存一个会话 ID；历史按倒序取最近若干条，未还原正序 可开多个会话并切换；历史按时间正序进入上下文，指代不再指向错轮次 待做
R-05 任务进度与流式队列迁出进程内存 任务状态与流式队列均为进程内变量 双 worker + 重启后，导入进度与流式答案都不丢 待做
R-06 修导入入口的后缀分支缺陷 分支判断把比较写成了赋值，PDF 分支实际走不进去 .md 与 .pdf 两条分支均可正常导入 已修

R-06 严格说是缺陷而不是需求，单独立一条是为了让它不被卷进排期讨论——它当天就该修完。

05决策记录

只记三类：改动大、可逆性差、且当时争议过的。每条都写清代价，因为没写代价的决策等于没做决策。

决策 D-01

型号确认的阈值不能拍，要穷举

选项
① 拍一个「看起来合理」的相似度阈值；② 按分数分布找断裂带，再做三级过滤；③ 永远追问，不做自动确认。
依据
把真实问句与库内型号的匹配分数画出来，0.5–0.6 之间存在一段明显的空档：匹配和不匹配之间有清晰间隔。这说明阈值是可被数据确定的，不该靠感觉。
结论
选②。三级过滤：高置信直接确认、中置信追问候选、低置信兜底引导；再穷举 189 组阈值组合定下三个切点。型号确认准确率 52.9% → 81.2%。
代价
中置信区间会多一轮追问。这是主动换来的：多问一句的成本，远低于答错型号让人去接错线。
决策 D-02

切片主键用结构，不用自增 ID

选项
① 沿用向量库的自增主键标评测集；② 用「文件::父标题::标题」这类结构路径做稳定主键。
依据
自增主键在每次重新导入后都会变，标注好的评测集会整体失联——这不是小麻烦，它会让「复测」这件事在第二次导入之后就做不了。
结论
选②。同一小节不再重复入库，切片重复率 31% → 0%、噪声率 21.7% → 0%；评测集用结构路径对齐，重导入后可复现。
代价
改标题就等于产生新片段。所以必须配一张版本表与别名映射，否则改一次目录就丢一次历史分数。
决策 D-03

拒答优先于多答

选项
① 尽量答，答不全也让模型凑一段；② 证据不足就让模型自评置信度，低于阈值转人工。
依据
两类错误的代价不对等。误放（该拒答却开口）会让人照着错的参数操作；误拦（本可答却转人工）只是多花人力。
结论
选②。阈值按「误放优先归零」来定，最终误放 0/240、误拦 15%。
代价
15% 的误拦是认下来的。后续想用一次低成本澄清追问（「你说的是哪一单 / 哪个型号」）把这部分捞回来，而不是直接转人工。
决策 D-04

确定性步骤固化，只把意图判断交给 Agent

选项
① 纯 Agent，工具全交模型调度；② 纯工作流；③ 混合——查单、查物流、退款流程写成固定步骤，Agent 只做意图判断与话术。
依据
纯 Agent 灵活但不可测，多轮之后会跳步；纯工作流可测但答不了开放问法。手册问答的失败代价高，可测性优先。
结论
选③。用结构限制代替提示词恳求，「不要跳步」不写进 prompt，而是让它没有跳步的路径。
代价
新增一种问法往往要改流程配置而不是改提示词，迭代速度慢一些。

06型号确认的三态

这一屏是整个系统最该被设计的地方。它不是一句提示语，而是一个有状态的分支：三种置信度对应三种完全不同的下一步， 且一旦确认就把型号锁进会话，后续轮次不再重新识别。

高置信不打扰、中置信给候选、低置信不猜。三档之间用穷举定的切点，不用单点阈值。

为什么必须有第三态。只有「确认 / 追问」两态时，所有不确定都涌进追问，用户会被反复问型号而放弃。 兜底态的作用是承认这次答不了，并明确告诉用户缺的是什么信息——这是把人导向人工，而不是让模型硬编一段。

为什么锁定这么重要。不锁定，用户每一轮都要重新说一次型号，多轮指代会飘；锁定之后， 「换了电池还要重新校准吗」这类承接上文的问题才有可能答对。锁定的作用域是会话，跨会话不继承，避免拿着旧型号答新问题。

07评测与验收口径

三层分开评，且每层都要能回答「样本多少、怎么标的、能不能复现」。没有这三件事的分数，只能当感觉用。

指标定义

指标口径用在哪一层
Recall@k前 k 个结果覆盖了多大比例的相关项检索层主指标
Hit@k前 k 个里是否至少命中一个相关项检索层辅指标，看「有没有救」
MRR / nDCG第一个相关项的位置倒数；按位置折损的排序质量排序质量，判断精排是否真的有用
引用可点率答案中角标能打开到原文片段的比例生成层，硬门槛 100%
误放 / 误拦该拒答却开口的比例 / 本可答却转人工的比例拒答层，两者必须分开报

两个数据集，各管一段

数据集规模用途已知局限
检索标注集 27 条人工标注（含标准答案片段） 跑 6 阶段消融，判断每一层组件是否真的带来增益 样本小，只够做方向判断，不能宣称泛化；下一步扩到 120 条以上
拒答五桶集 300 题，其中 240 题可作答 把「答得准」和「知道什么时候别答」拆开评 题目自建，不等于线上真实分布；阈值仍需真实会话校准

标注规范上，每条金标引用支持「同文件 + 同父标题」的与约束匹配，而不是只对到文件级——只对文件级的标注， 在长手册上几乎必然虚高。数据集导入时还要与语料做一次存在性校验，避免标注指向了已被删除或改名的片段。

6 阶段消融（27 条标注）

阶段增量组件Recall@5判断
S1仅稠密检索0.759基线。型号字母数字混写时最弱
S2+ 稀疏检索—补上型号这类精确 token 的召回
S3混合检索—两路互补，进入可用区间
S4+ HyDE + RRF—口语长尾问法改善最明显
S5+ 精排—排序质量提升，Hit@5 同步上行
S6全链路0.981Hit@5 由 0.778 到 1.000

0.759 → 0.981 是初步验证，不是结论：27 条标注上每一条的权重都很重，换一批题结论可能变。所以消融的用途是「哪一层值得留」， 而不是对外宣称检索水平。

验收门槛

验收项门槛不达标时的处理
检索 Recall@5≥ 0.95先查索引健康度（重复率、噪声率），再动检索参数
引用可点率100%视为缺陷，不带病上线
无依据作答率≤ 1%收紧拒答阈值，接受误拦上升
旧版召回0 次阻断：文档生命周期未修完不发版

08排期

按「修完能解锁什么」分三档，而不是按功能清单平均分配。

档位内容解锁什么
1–2 周
必须修		 导入入口缺陷；按文档删除与重传；结构化引用回传；多会话 + 历史正序 + 型号锁定；任务与流式状态外置 从「能演示」到「能连着用一天」
2–6 周
护城河		 型号候选 chip 交互；检索调试台（三路召回 + 融合分 + 精排分 + 截断点）；文档工作台与切片预览；反馈闭环与离线评估集；图片落库与重试 把「更准」变成用户能看见、能自己调的东西
持续
演进		 鉴权与多租户；多格式与增量解析；成本与 trace 可观测；切分重叠与提示词版本化 从单个班组用，推到多团队用

09风险与开放问题

风险影响应对
标注集太小27 条上的提升可能不成立扩到 120 条以上再对外报数；当前只当方向判断
阈值与品类强绑定换一类设备，断裂带位置会变把阈值做成应用级配置，换品类时重跑一次分数分布
联网结果压过手册答案来源不可控，售后不敢用联网结果在融合里设权重上限，且必须标注来源为「外部」
多 worker 下的内存态首次真实部署必现丢流迁出进程内存（P0 R-05），不做「演示够用」的妥协
标题改名即新片段历史分数无法对齐版本表 + 别名映射，评测集按别名回溯
还没想清楚的一件事：型号锁定的作用域。锁在整个会话最简单，但用户换设备提问时会拿到旧型号的答案； 锁在「话题」上更合理，可话题边界怎么判、判错的成本多大，目前没有数据支撑。先按会话锁，把「手动解除锁定」做成可见入口， 等真实会话攒够再做话题级。

10附：与成熟产品的能力对照

选同赛道产品化最完整的那个来对照，只问一件事：用户在它那里已经习惯的能力，我们有没有。 这张表直接决定了 R-01 到 R-04 的优先级——不是竞品有我们就要有，而是缺了它用户就得在两个工具之间来回切。

能力成熟产品本系统结论
查询时实体确认 按元数据字段筛，不解决「用户没报型号」 抽型号 → 向量对齐 → 歧义确认 → 按型号收窄 优势，要兑现成交互
多路融合与精排 加权检索 + 外部精排 三路并行 + 融合 + 断崖截断，链路显式可解释 优势，别藏起来
引用溯源 默认角标，点开即片段 片段 ID 有了，但没回传给前端 必须补
文档管理 列表、版本、删除、切片预览齐全 只进不出 必须补
参数可调 调试台可视化改 TopK / 权重 / 阈值 参数在代码里，运营改不了 排 P1
多知识库与权限 企业标配 单集合、无鉴权 本期不做

一句话结论：算法层已经站得住，产品层最大的缺口是「可治理、可信任、可调参」。 把引用、文档生命周期、型号确认交互做实，比再加一个检索技巧更能换回日常信任。
